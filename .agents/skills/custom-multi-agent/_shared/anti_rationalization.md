# 합리화 방지 패턴 (Anti-Rationalization)

> **읽어야 하는 시점**: Tier를 판정할 때, 그리고 규칙을 건너뛰고 싶은 충동이 들 때.
> 이 문서를 읽지 않고 Tier를 낮추거나 단계를 생략하는 것은 규칙 위반이다.

## 공통

| 에이전트의 변명 | 올바른 대응 |
|---|---|
| "이건 간단한 작업이라 바로 코딩해도 됩니다" | 간단한 작업이야말로 검증되지 않은 가정이 가장 위험합니다. Tier를 판정하십시오. |
| "먼저 코드베이스를 탐색해야 합니다" | 스킬 규칙을 먼저 확인하십시오. 스킬이 탐색 방법을 안내합니다. |
| "더 많은 컨텍스트가 필요합니다" | 스킬 확인은 명확화 질문보다 먼저입니다. |
| "이건 스킬/규칙의 정신을 따르고 있습니다" | **규칙의 문자를 위반하는 것은 정신을 위반하는 것입니다.** |
| "이미 확인했으니 검증을 건너뛰겠습니다" | 확신 ≠ 증거. 검증을 실행하십시오. |
| "워커를 호출하기엔 너무 사소한 변경입니다" | 오케스트레이터 직접 수정 금지에 예외는 없습니다. Tier와 무관합니다. |
| "브리프에 코드가 인용돼 있으니 파일을 다시 읽을 필요는 없습니다" | 스냅샷은 낡습니다. 실제 회귀 사고가 발생한 지점입니다. 라이브 파일을 읽으십시오. |
| "계획이나 마일스톤 정도는 오케스트레이터가 직접 세워도 됩니다" | 오케스트레이터는 관리자이자 조율자입니다. 아키텍처 분석, 마일스톤 기획, 세부 설계는 `planner` 워커에게 100% 위임하십시오. |
| "워커를 부르기 전에 내가 먼저 분석하고 로드맵을 다 짜놓겠습니다" | 브리프에는 대상 경로·라인 범위·지시만 담아 `planner`를 호출하십시오. 오케스트레이터의 추론 독점은 멀티에이전트 역할 분담 위반입니다. |

## Tier 판정 전용

| 에이전트의 변명 | 올바른 대응 |
|---|---|
| "느낌상 Tier 1로 봐도 될 것 같습니다" | 느낌은 판정 근거가 아닙니다. 4개 객관 기준을 각각 **수치로** 적으십시오. |
| "파일이 3개지만 다 사소하니 Tier 1입니다" | 기준은 "사소함"이 아니라 파일 수입니다. 3개면 Tier 2입니다. |
| "핫스팟인지 확실하지 않지만 아마 아닐 겁니다" | 불확실하면 **상위 Tier**입니다. 그것이 fail-safe 방향입니다. |
| "작업 도중 범위가 커졌지만 이미 Tier 1로 시작했으니 계속합니다" | 즉시 Tier 2로 승격하고 사용자에게 고지하십시오. |
| "시간을 절약하기 위해 단계를 합쳤습니다" | Tier가 허용한 병합만 가능합니다. 임의 병합은 금지입니다. |
| "크리틱이 확실히 통과할 내용이라 생략합니다" | 크리틱 생략은 어떤 Tier에서도 허용되지 않습니다. 모델 등급만 달라집니다. 실측상 35개 태스크 중 17개가 이 변명으로 크리틱 0건이었습니다. |

## 루프 및 기록 전용

| 에이전트의 변명 | 올바른 대응 |
|---|---|
| "이번 교정이면 확실히 통과할 테니 한 번만 더" | 워커 호출 4회가 상한입니다. 3회 교정해도 안 되면 브리프나 설계가 틀린 것입니다. 에스컬레이션하십시오. |
| "승인은 대화에서 받았으니 로그는 나중에 몰아서" | 나중은 오지 않습니다. 실측상 35개 중 21개가 승인 기록 0건입니다. 받는 즉시 남기십시오. |
| "계측은 작업과 무관하니 나중에 돌리겠습니다" | `--strict`가 통과해야 `[COMPLETE]`를 남길 수 있습니다. 순서를 바꾸지 마십시오. |
| "결과가 조금 잘린 것 같지만 핵심은 다 들어있습니다" | exit code 3은 불완전의 증거입니다. 잘린 diff를 병합하면 조용히 깨집니다. 범위를 쪼개 재호출하십시오. |

## 병렬 실행 전용

| 에이전트의 변명 | 올바른 대응 |
|---|---|
| "파일이 많으니 일단 전부 다른 그룹으로 쪼개 병렬로 돌리겠습니다" | 그룹은 파일 수가 아니라 **의존 관계**로 나눕니다. 심볼을 주고받는 파일을 쪼개면 서로 어긋난 코드가 나옵니다. |
| "의존 관계가 애매하지만 아마 독립일 겁니다" | 애매하면 **같은 그룹**입니다. 병렬화 실패는 되돌리기 비쌉니다. |
| "그룹 A는 통과했으니 먼저 반영해두겠습니다" | 부분 병합 금지. 중간 상태에서 컴파일이 깨집니다. 전 그룹 통과 후 한 번에 반영하십시오. |
| "그룹별 비평은 나중에 한꺼번에 하겠습니다" | 그룹 result가 나오는 즉시 그 그룹 비평을 붙입니다. 몰아서 하면 병렬화로 아낀 시간이 사라집니다. |
| "그룹이 1개로 나왔지만 그래도 둘로 나눠 병렬로" | 그룹이 1개면 병렬화하지 않습니다. 억지 분할이 가장 흔한 실패입니다. |

## 브리프 및 재비평 전용

| 에이전트의 변명 | 올바른 대응 |
|---|---|
| "워커가 맥락을 알아야 하니 브리프에 코드를 넣겠습니다" | 워커는 라이브 파일을 직접 읽습니다. 브리프는 경로·라인 범위·지시만 담습니다. 상한 초과 시 `call_worker.py`가 exit 4로 기동을 차단합니다. |
| "브리프가 조금 길지만 내용이 다 필요합니다" | 실측에서 브리프가 워커 결과물의 2.7배였습니다. 배경 설명과 이전 라운드 요약부터 덜어내십시오. |
| "재비평이니 처음부터 전체를 다시 보겠습니다" | 2회차부터는 직전 지적 항목과 그 구간만 봅니다. 전체 재감사는 금지입니다. |
| "문서라서 diff가 없으니 전문을 매번 읽어야 합니다" | 섹션 앵커로 지적하고, 지적한 섹션만 다시 읽으십시오. 원문 복사 대신 `파일#섹션명`으로 인용하십시오. |
